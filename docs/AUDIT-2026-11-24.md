## Constats démontrés et corrigés

### A1 — Limites de débit de l'API contournables (P1, sécurité)
| Élément | Contenu |
|---|---|
| Problème | Toutes les limites de débit de l'API (globale 120/min, suppression de compte 3/min, invitations e-mail 10/min, file 6/min) se contournent en envoyant un en-tête `X-Forwarded-For` différent à chaque requête. |
| Gravité | Abus possible des routes sensibles (tentatives répétées, envois d'invitations). Atténué pour les e-mails par les plafonds en base (1/heure/adresse, 50/jour/cagnotte). |
| Reproduction | Distant, sans compte : 8 × `POST https://complice-api.onrender.com/internal/outbox/drain` (route sans effet de bord). Même client : `200×6 429 429`. Avec `X-Forwarded-For: 203.0.113.<n>` différent : `200×8`. |
| Cause | `backend/src/app.ts` : `trustProxy: true` fait confiance à toute la chaîne ; l'adresse retenue est la plus à gauche, fournie par le client. |
| Correction | Nombre de relais de confiance configurable (`TRUST_PROXY_HOPS`, 1 par défaut pour Render) : l'adresse retenue est celle ajoutée par le dernier relais. |
| Validation | Local : test `limite de débit : une adresse forgée…` (7e appel 429). Comparaison Fastify : `trustProxy: true` → `200×8`, 1 relais → `200×6 429 429`. |
| Limite | Effectif en production après le déploiement manuel de Render ; l'essai distant sera refait après. Si Render ajoute plusieurs relais, ajuster `TRUST_PROXY_HOPS`. |

### A2 — Ouverture de la capsule déplaçable dans le passé (P1, perte de données et accès anticipé)
| Élément | Contenu |
|---|---|
| Problème | Un organisateur ou coorganisateur pouvait fixer `reveal_at` dans le passé : capsule ouverte immédiatement et irréversiblement, la personne fêtée lisait les mots avant la date annoncée, les brouillons des autres restaient définitivement hors de la capsule (plus modifiables). |
| Gravité | Résultat métier incorrect et irréversible ; la création refusait déjà une date passée (`reveal_in_past`), pas la modification. |
| Reproduction | Local : compte coorganisateur, `update events set reveal_at = now() - 1 h` (+ clôtures antérieures) → accepté avant correction (test rouge). |
| Cause | `events_guard()` contrôlait l'ancienne date (déjà passée), pas la nouvelle. |
| Correction | Migration 14 : `events_guard()` refuse une nouvelle ouverture ≤ maintenant (`reveal_in_past`, message déjà traduit dans l'app). |
| Validation | Local : `audit.test.mjs` (refusé pour organisateur et coorganisateur, capsule toujours scellée, avancer à une date future reste possible) ; paquet `apply-14.sql` rejoué sur une copie avec données : refus confirmé. |
| Limite | Effectif après application de la migration 14. |

### A3 — La page d'un lien d'invitation dévoilait la surprise (P1, confidentialité)
| Élément | Contenu |
|---|---|
| Problème | `/i/<jeton>` affichait « Tu es invité·e à préparer un cadeau commun » à tout le monde, y compris la personne fêtée invitée par e-mail. |
| Gravité | Contredit le parcours bénéficiaire (rien des préparatifs avant l'ouverture). |
| Reproduction | Personne fêtée invitée par e-mail → lien de l'e-mail → page web. |
| Cause | `backend/src/invite-page.ts` : texte unique (la page ne lit pas la base, donc ne connaît pas le rôle). |
| Correction | Texte neutre (« invitation personnelle »), titre « Complice », aucune balise de partage. |
| Validation | Local : test `pages publiques…` (aucun mot « cadeau / surprise / cagnotte », `noindex, nofollow`, `no-referrer`). |
| Limite | En production après déploiement Render. |

### A4 — Métadonnées des photos conservées (P1, confidentialité)
| Élément | Contenu |
|---|---|
| Problème | Les octets de l'image choisie étaient envoyés tels quels : position GPS, appareil, date de prise de vue, commentaires restaient dans le fichier lisible par le groupe ou la personne fêtée. |
| Gravité | Fuite de localisation possible (domicile). Certain sur le web (fichier original) ; sur téléphone, dépend du ré-encodage du sélecteur (non mesuré). |
| Reproduction | Code : `lib/media.ts` → `uploadImage` envoyait `readBytes()` sans traitement. Test : un JPEG avec segment Exif « GPSLatitude » ressortait identique. |
| Correction | Préparation à la sélection (`expo-image-manipulator`, web et natif) : côté long ≤ 1 600 px, ré-encodage JPEG 0,82 ; puis `stripImageMetadata()` à l'envoi (JPEG : APP1/APP13/APP3-15 sauf Adobe/COM ; PNG : tEXt/iTXt/zTXt/eXIf/tIME). |
| Validation | Local : test `métadonnées : GPS, appareil et commentaires retirés` (JPEG, PNG, structure inconnue laissée intacte). |
| Limite | Téléphone non essayé ; HEIC/WebP non nettoyés si la préparation échoue (repli sur l'original). |

## Observations non corrigées (avec raison)
- `select_gift` sur une cagnotte non active crée encore activité et notifications ; prendre/terminer une mission ne
  vérifie pas le statut. Les statuts non actifs ne sont posés que par l'administration : non atteignable par un client.
- Deux requêtes `event_members` à l'ouverture d'un écran de cagnotte (rôle pour l'aiguillage + liste des membres) :
  coût mesuré faible (une requête de quelques centaines d'octets) ; l'aiguillage doit décider avant le chargement des pages.
- La recherche de pseudo (2 caractères minimum, sans e-mail) permet d'énumérer des pseudos et prénoms ; choix produit à arbitrer.
- CORS de production : origines locales de développement autorisées (sans effet pratique : authentification par
  en-tête, pas de cookie). `/health` indique si l'admin et l'e-mail sont configurés.
- Render ne se redéploie pas automatiquement (constaté depuis plusieurs lots).

## Vérifications de sécurité effectuées (périmètre réel)
- **Base distante, lecture seule** : 60 fonctions exposées aux comptes connectés, toutes `search_path=''`, une seule ouverte
  aux visiteurs (`preview_invitation`) ; contrôles internes relus pour les fonctions qui reçoivent un identifiant
  (rôles, transfert, missions, votes, contributions, suppression de compte) ; droits par colonne (écritures limitées
  aux colonnes prévues, colonnes protégées par déclencheurs) ; politiques RLS ; contraintes de longueur et de format
  (liens d'idée `http(s)` seulement : pas de `javascript:`) ; buckets privés, 2 et 5 Mo, types image.
- **Distant, 37 essais ciblés** (`pentest-remote.mjs`, comptes de démo) : personne extérieure connaissant l'identifiant
  d'une cagnotte (10 tables, 5 fonctions, écritures, lien d'invitation, liste des fichiers) ; participant (se nommer
  organisateur, changer de rôle, transférer, renommer, régler ou modifier une participation, lire celles des autres,
  montants nominatifs, message au nom d'un autre, file d'e-mails) ; recherche sans e-mail ; personne fêtée (notifications) ;
  visiteur non connecté. **Aucun accès indu sur ces essais.**
- **Personne fêtée** : essais réels avant/après l'échéance du lot 10 (API, médias, préparatifs, brouillons) ; export
  testé localement (rien de la surprise avant l'ouverture).
- **Secrets** : aucune clé secrète dans le dépôt ni l'historique Git ; `.env` et comptes de test ignorés ; seules
  l'URL Supabase, la clé publique et l'URL de l'API sont exposées à l'app.
- **Session et cache** : cache des requêtes vidé à chaque connexion, déconnexion ou réinitialisation ; brouillons
  locaux effacés à la déconnexion ; abonnements temps réel fermés au démontage.
- **Entrées** : montants (`-5`, `1e3`, trois décimales refusés ; plage 1–1 000 € revérifiée en base), textes bornés,
  jetons et identifiants validés côté API.
- **Non testé** : limites serveur de Supabase Auth sur les codes (pas d'essai de force brute, par principe) ; flux temps
  réel directement (la RLS s'applique aux changements diffusés) ; dépendances vulnérables (pas d'audit `npm audit`
  exploité dans cet audit) ; infrastructure Supabase, Render, Brevo (hors périmètre).
